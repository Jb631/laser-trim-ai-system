# Session 2026-07-09 — Work deployment incident: processing "locked up"

## Report
First day at work: "went to process files and the app completely locked up,
it wouldnt process anything … it started reprocessing all files and didnt
recognize any files in the db, and then was hit with errors while trying to
save to the db."

## Diagnosis (from code; work log still wanted for confirmation)
Incremental recognition was an EXACT full-path string match against paths
stored in the database, and a miss meant "definitely new" with no fallback.
Any difference in path FORM between how the share was browsed when the rows
were written and how it was browsed yesterday (mapped drive letter vs UNC vs
a different root, or a case difference) makes every lookup miss:
0 of N recognized → the app sets out to re-parse the entire known history
over the share (the "locked up" hours) → every save bounces off the
(filename, file_date, model, serial) unique constraint (the "errors saving").
A second candidate with identical symptoms: the app pointed at a fresh/empty
database (data/ is gitignored — a clean clone has no data folder).
A third defect made it LOOK dead: the processing worker caught only
StopIteration — any other exception killed the thread silently, leaving the
Start button disabled forever and no message on screen.

## Fixes (all in commit for 2026-07-09)
1. **Basename rescue** (core/processor.py): on a full-path miss, recognition
   falls back to the FILENAME (filenames carry model_serial_datetime):
   recorded (size, mtime) match → skip and re-bind the new path form, no file
   read; a UNIQUE legacy record with no recorded stat (databases predating
   the stat fast-path — the work DB) → adopted with the observed stat, no
   file read; ambiguous cases → the existing hash identity check. This also
   kills the first-scan hash storm the work DB would otherwise have hit.
2. **Runaway-reprocess guard**: a NON-empty database that recognizes 0 files
   in a ≥50-file batch aborts with a plain-language message (wrong path form
   or wrong database; uncheck incremental to force). An empty database passes
   through (legitimate first run).
3. **Worker hardening** (gui/v6/pages/process_page.py): any exception in the
   processing thread now surfaces as "Stopped: …" in the progress area and
   re-enables Start — the silent-dead-thread lockup cannot recur.
4. **Duplicate saves are skips**: a UNIQUE-constraint hit on save counts as
   "already in database", not an error storm.
5. **Database indicator on the Process page**: shows the DB path and unit
   count before Start — an empty/wrong database is now visible at a glance
   ("⚠ EMPTY database" warning).

## Tests

Plus the existing stat fast-path suite still green. App sweep 45/0.
